# P4-C/D — Claim review, model pricing and cost governance

Status: feature-branch candidate. The implementation does not certify diagnosis truth and does not authorize automatic control or model-driven changes to the original diagnosis.

## 1. P4-C: claim review lifecycle

The external diagnosis analysis emits a host-owned \`claim_governance\` record. Each claim has a stable ID, source-bound evidence and an epistemic status:

- \`REPORTED\`: the source explicitly states the observation.
- \`DERIVED\`: deterministic calculation from supplied values.
- \`INFERRED\`: interpretation or hypothesis generated by the model.

Hypotheses default to \`INFERRED\` in host code. A model cannot write \`EXPERT_CONFIRMED\`. All claims start with \`expert_review_status=PENDING\`.

An optional independent verifier can be selected through \`phase_engine_ids.verification\`. It must have a distinct model identity from the analysis model. It receives only claim text and original source text, not the generator's reasoning or chosen citations. Its assessments are evidence-support review aids, not factual certification. The UI keeps model-selected references separate from independent-review references.

The existing expert review workspace is reused:
- \`GET /v1/platform/material-knowledge/report-reviews/{job_id}\`
- \`POST /v1/platform/material-knowledge/report-reviews/{job_id}/claims/{claim_id}/decisions\`

The review requires an authenticated expert session and CSRF token. Decisions are append-only and hash-chain verified. \`ACCEPT\`, \`REJECT\`, \`REVISE\`, and \`NEEDS_EVIDENCE\` require a reason and independent evidence reference (except the evidence-gap decision). A revision creates a review event; it does not mutate the immutable model report. The exported feedback is not automatically training-authorized. Each claim snapshot records the generating model and (when configured) the independent verifier model. The export includes a per-generator-model count of ACCEPT / REJECT / REVISE / NEEDS_EVIDENCE / pending outcomes. These are expert-feedback counts, **not accuracy scores**; comparisons require adequate sample size, reviewer agreement and comparable case mix.

## 2. P4-D: administrator-managed price book

Prices are never guessed or fetched implicitly. An administrator explicitly adds a price version with:
- provider ID and exact model ID;
- currency;
- input/output price per one million tokens;
- effective time with timezone;
- source type (\`OFFICIAL_PUBLISHED\`, \`CONTRACT\`, \`ADMIN_ESTIMATE\`);
- traceable source reference or contract record.

The UI is under **大模型配置 → 模型价格与费用核算**. In Bearer mode, the page accepts a temporary administrator token in memory only. Local mode requires no token.

API:
- \`GET /v1/platform/settings/model-pricing\`
- \`POST /v1/platform/settings/model-pricing\`

Example body:

\`\`\`json
{
  "provider": "openai",
  "model": "exact-model-id",
  "currency": "USD",
  "input_per_million_tokens": "2.50",
  "output_per_million_tokens": "10.00",
  "effective_from": "2026-11-06T00:00:00+00:00",
  "source_type": "OFFICIAL_PUBLISHED",
  "source_ref": "official pricing page / dated contract reference"
}
\`\`\`

The local SQLite price book is append-only. An existing price version cannot be updated or deleted. A change creates a new revision with a new effective time. At request start, the execution journal resolves and freezes the applicable price snapshot. Later price changes do not rewrite historical run receipts.

For each recorded HTTP attempt the journal retains:
- provider and exact model ID;
- stage and request digest;
- token usage returned by the provider;
- pinned price ID/revision and source reference;
- estimated cost and currency, when computable.

Cost calculation:

\`\`\`text
estimated_cost =
  input_tokens  × input_price_per_million  / 1,000,000
+ output_tokens × output_price_per_million / 1,000,000
\`\`\`

The calculation uses decimal arithmetic and stores 12 fractional currency digits. It covers provider token charges only. It excludes hosting, local GPU/electricity, taxes, negotiated discounts, cached-token discounts and other provider-specific billing components unless they are explicitly modeled later.

### Cost status semantics

| Status | Meaning |
|---|---|
| \`CALCULATED\` | All recorded requests have a pinned price and complete token usage in one currency |
| \`PRICING_NOT_CONFIGURED\` | At least one response has usage but no matching price version |
| \`USAGE_INCOMPLETE\` | A response was received but complete token usage was not returned |
| \`POSSIBLE_UNMETERED_BILLING\` | A request failed, was interrupted or timed out after dispatch; the provider may still have billed it |
| \`MIXED_CURRENCY\` | Requests in one run have different currencies; no combined total is shown |
| \`NO_REQUESTS\` | No model request was recorded |

Missing usage is never converted to zero. A timeout is not assumed to be free. Local/self-hosted inference is not automatically labeled zero-cost; infrastructure cost is outside this token ledger.

## 3. Execution view

The shared execution view shows per-run and per-request:
- stage, provider/model, transport status, HTTP status and latency;
- input/output token counts;
- pinned price result and estimated cost;
- explicit warning when pricing or usage is missing, or a request may have been billed without a returned receipt.

Old execution receipts remain readable. They are not retroactively priced; their cost status remains unpriced/unknown according to the available historical data.

## 4. Validation

The source regression covers:
- price version resolution by effective time;
- append-only update/delete rejection;
- decimal arithmetic and missing-usage behavior;
- immutable per-request price snapshots;
- possible billing after transport failure;
- administrator API registration;
- generated claim registry → independent review → authenticated expert decision;
- immutable source report and hash-chain feedback export;
- UI asset versioning and execution cost rendering.

A passing CI result validates engineering behavior only. It does not establish real provider pricing correctness, model reasoning quality or scientific truth. Administrators must verify the source and effective date of every registered price. Production-model quality requires representative blind expert evaluation and is a separate acceptance gate.
